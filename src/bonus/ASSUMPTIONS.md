# Assumptions and decisions

This file records every assumption or implementation choice that is **not** explicitly stated in Wadhawan (2021), *AraBERT and Farasa Segmentation Based Approach For Sarcasm and Sentiment Detection in Arabic Tweets* (arXiv 2103.01679), EACL WANLP-2021 Shared Task 2, Subtask 2. Where applicable, the same choice is also noted in a code comment or docstring near the implementation.

## Phase A — Exploratory data analysis

- **Raw schema.** The raw files were inspected before writing code. They contain exactly `tweet`, `sarcasm`, `sentiment`, and `dialect`. `sarcasm` is parsed by pandas as a boolean, `sentiment` and `dialect` as strings, and `tweet` as a string.
- **Test labels are real.** The test file contains a populated `sentiment` column with only `POS`, `NEG`, and `NEU`. These labels are treated as held-out gold. They are never used for training, hyperparameter tuning, or model selection; only the separate final evaluation function may read them.
- **Duplicate and overlap matching.** Duplicate counts and the primary train/test overlap check use exact string equality on the raw tweet text. A separate normalized overlap check strips leading/trailing whitespace and collapses internal whitespace runs. Neither check applies Unicode normalisation or lowercasing.
- **Character length.** Tweet length in characters is the number of Unicode code points (`len` on the Python string), not the number of grapheme clusters.
- **Whitespace-token length.** Whitespace-token length is the number of tokens produced by Python's `str.split()` with no arguments.
- **AraBERT token length.** Token lengths come from `aubmindlab/bert-base-arabertv02` with `add_special_tokens=True`, no truncation, and no padding. The reported length therefore includes `[CLS]` and `[SEP]`.
- **Paper comparison.** The paper reports 12,548 training rows, about 17% positive examples, and a 90:10 split of 11,293 training / 1,255 validation rows. The EDA compares the observed row count and positive share directly; the split sizes are compared in Phase B.
- **EDA does not modify data.** No rows are dropped, deduplicated, or relabelled during Phase A.

## Phase A review decisions

- **Paper title.** The title is recorded as *AraBERT and Farasa Segmentation Based Approach For Sarcasm and Sentiment Detection in Arabic Tweets* (Wadhawan, arXiv 2103.01679) in the notebook and in this file.
- **Plot palette.** All EDA figures use shades of blue only (`BLUE_DARK`, `BLUE_MEDIUM`, `BLUE_LIGHT`).
- **Neutral label check.** `check_sentiment_labels` returns a split-independent verdict (`VALID SENTIMENT LABELS` or `EMPTY OR PLACEHOLDER LABELS`). The held-out-gold warning is printed only in the notebook cell that checks the test split.
- **Conflicting duplicate labels.** Conflicting sentiment labels are detected only for tweets whose exact text appears more than once, consistent with the exact duplicate counts. No whitespace normalisation is used for this check. In the training file this finds 25 repeated tweets covering 50 rows.
- **Normalized overlap.** The normalized overlap strips leading/trailing whitespace and collapses internal whitespace runs, but does not lowercase, remove punctuation, or apply Unicode normalisation. For this dataset it finds the same 2 overlapping tweets as the exact check.
- **Marker definitions.** URLs match `https?://\S+|www\.\S+`, mentions match `(?<!\w)@\w+`, and hashtags match `(?<!\w)#\w+`. `\w` is Unicode-aware, so Arabic letters are included.
- **Marker ratio.** Tokens-per-word ratios in the marker breakdown are aggregate ratios (total AraBERT tokens divided by total whitespace tokens for the relevant subset), not the mean of per-tweet ratios. AraBERT token counts include special tokens.
- **Label shift.** The train/test sentiment label shift is reported in the notebook summary but is not corrected in EDA; no resampling, reweighting, or relabelling is applied.

## Phase B — Preprocessing and split

- **Single preprocessing function.** `src/bonus/preprocessing.py::preprocess_text` is the only cleaning function. It is applied to train, validation, and test.
- **No Farasa segmentation.** Farasa is not used because `bert-base-arabertv02` was not pre-segmented (paper Table 1).
- **Placeholder tokens.** URLs become `[رابط]`, emails become `[بريد]`, and mentions become `[مستخدم]`. The paper text literally maps emails to `مستخدم` and mentions to `بريد` (swapped, likely a typo); we follow the AraBERT convention (email = `بريد`, mention = `مستخدم`). Private-use sentinels keep these placeholders intact while whitespace is inserted.
- **URL boundaries.** A URL match stops at whitespace, `#`, or any non-ASCII character, so a hashtag or Arabic text glued to a URL survives as a separate token. For example, `https://t.co/abc123#مصر` becomes `[رابط] #مصر`, and `https://t.co/cN7dLaIhnJ#tag1#tag2` becomes `[رابط] # tag 1 # tag 2`. The same rule applies to `www.` URLs. This changed the preprocessed text of 521 of 11,293 split-train tweets, 62 of 1,255 validation tweets, and 12 of 3,000 test tweets (4.61%, 4.94%, and 0.40%).
- **Replacement order.** URLs, emails, and mentions are replaced before whitespace insertion. The paper lists replacement as step 4, but doing it after whitespace insertion would split URLs and placeholders. This is an implementation-order decision.
- **Emoticon removal.** Text emoticons are removed with a regex. Emoticons that start with `:`, `;`, or `=` and symbol emoticons such as `<3`, `^_^`, `-_-`, and `T_T` are removed. Emoticons that start with a letter or digit are removed only from an explicit whitelist (`xD`, `XD`, `D:`, `D=`, `8)`, `8-))`), guarded by `(?<!\w)` and `(?!\w)`. This avoids false positives such as `[الزخرف:18]`, `Naxos`, `Dell XPS 13`, `SA8*`, and `m8S`. Emoji and other Unicode symbol characters (category `So`), private-use/unassigned/surrogate characters (`Co`, `Cn`, `Cs`), format characters (`Cf`), control characters (`Cc`), variation selectors, zero-width joiners, and keycap combiners are also removed. The three internal private-use sentinels are exempted. The paper describes emoticons and non-ASCII emojis as unwanted characters.
- **HTML tags.** Only real tag shapes are removed: a letter must follow `<` or `</`. This prevents text such as `<3 ... >_<` from losing the span between `<` and `>`.
- **Repeated characters.** Runs of more than two identical non-digit characters are collapsed to two. Digits are not collapsed. This follows the AraBERT `_remove_non_digit_repetition` behavior and the paper's `>2` wording.
- **Whitespace insertion (documented deviation).** The official AraBERT preprocessor inserts spaces around every character outside Arabic letters/digits, Latin letters/digits, and brackets (i.e. around punctuation). Our implementation instead inserts spaces around Latin runs, Western digit runs, and square brackets only. BERT's BasicTokenizer splits punctuation anyway, so most of the difference is absorbed downstream. The visible difference is that `#COVID19` becomes `# COVID 19`, while an Arabic hashtag such as `#فلول` stays intact. Other punctuation (except `/`, which becomes ` - `) is left attached.
- **Tashkeel and tatweel.** Tashkeel (`U+0617–U+061A`, `U+064B–U+0652`) and tatweel (`U+0640`) are stripped inside `preprocess_text`, in the same early removal stage as invisible/private-use characters, before repeated-character collapsing and whitespace insertion. The paper does not list this step explicitly, so it is a documented decision. Justification: the paper states that it follows AraBERT preprocessing, and the official AraBERT preprocessor strips tashkeel and tatweel by default; the measured `[UNK]` reduction on train/validation also supports it (total `[UNK]` 4,755 → 1,136 on train and 579 → 172 on validation; tweets with at least one `[UNK]` 19.11% → 4.54% on train and 18.09% → 4.70% on validation). The same stripping is applied identically to every model. Decision: strip tashkeel and tatweel. Measurement note: the `4,755 → 1,136` (train) and `579 → 172` (validation) totals, and the matching percentage figures, come from the earlier scratch comparison, which used a wider scratch tashkeel/tatweel regex than the final code. The final code strips only the narrower ranges listed above. With the pipeline as it now stands, the current `[UNK]` totals are **229 on train** and **29 on validation** (`1,150` and `174` immediately before the final Fitzpatrick/NFKC/slash pass).
- **Fitzpatrick skin-tone modifiers.** The modifiers `U+1F3FB–U+1F3FF` are removed in the same early removal stage as emoji. This is our decision, not a paper statement. Measured on the pre-change split text, 149 modifiers in 122 split-train rows, 14 in 13 validation rows, and 32 in 30 test rows are removed. The change is applied identically to every model.
- **Arabic Presentation Forms normalization.** NFKC is applied only to characters in `U+FB50–U+FDFF` and `U+FE70–U+FEFF`, before repeated-character collapsing and whitespace insertion; the rest of the string is not normalized. This is our decision, not a paper statement. Measured on the pre-change split text, 2,274 presentation-form characters in 126 split-train rows, 425 in 16 validation rows, and 406 in 19 test rows are normalized. Together with the other final changes, this reduces total `[UNK]` from 1,150 to 229 on train and from 174 to 29 on validation. The change is applied identically to every model.
- **Slash replacement.** `/` is replaced with ` - ` before the final whitespace collapse, after URLs, emails, and mentions have been replaced by placeholders, so placeholders are unaffected. This follows the official AraBERT v02 preprocessor. This is our implementation decision, not a paper statement. Measured on the pre-change split text, 195 slashes in 147 split-train rows, 24 in 17 validation rows, and 50 in 30 test rows are replaced. The change is applied identically to every model.
- **Decision evidence and test isolation.** The Fitzpatrick, selective-NFKC, and slash decisions were based only on train and validation `[UNK]` analysis. Every test-set count reported in this file is report-only: it influenced no preprocessing decision, and test labels were never used for any decision.
- **Preprocessing frozen.** The preprocessing pipeline is now frozen. No further changes will be made without a new documented review; every model uses this exact `preprocess_text`.
- **Arabic-Indic digits.** Arabic-Indic digits (`U+0660–U+0669`, `U+06F0–U+06F9`) are not mapped to Western digits and are not treated as Western digits. 305 of the 12,548 official training tweets contain them (279 in the 11,293-row split train).
- **Label mapping.** The fixed mapping is `NEG=0`, `NEU=1`, `POS=2` (alphabetical order). It is defined once in `src/bonus/data.py`.
- **Split settings.** The split is stratified on the sentiment label only, with the seed from `configs/bonus/split.yaml` (seed 42), using `sklearn.model_selection.train_test_split`. The resulting sizes are 11,293 train and 1,255 validation, matching the paper. The paper's validation counts deviate by about 20 to 25 rows from the sentiment-stratified expectation; this suggests (inference, not fact) that the paper did not stratify on sentiment. Text-only duplicate checks find that 13 of the 1,255 validation texts also appear in train (6 with a different label), and 6 test rows (5 distinct texts) appear in train or validation.
- **Duplicates are kept.** The 25 training tweets with conflicting sentiment labels and all other duplicate tweets are retained. The stratified split may place conflicting copies on both train and validation sides. This is accepted to preserve the official training rows.
- **No rows dropped.** No row is removed after preprocessing; in the current data no preprocessed tweet is empty. Retaining every row preserves the paper's split sizes.
- **Test isolation.** The test file is preprocessed with the same function and saved with its labels for the separate final evaluation. Its labels are never used for splitting, tuning, or model selection. Text-only token and marker statistics are computed on test for the requested before/after comparison.
- **Saved files.** `data/splits/arsarcasm_v2/train.csv`, `validation.csv`, and `test.csv` contain exactly `text,label` and are UTF-8 encoded.
- **Token comparison.** Before/after statistics use the same AraBERT tokenizer and marker regexes as Phase A. The additive helper `src/bonus/eda.py::token_statistics` reports the token statistics; it does not change Phase A logic. Token counts include `[CLS]` and `[SEP]`. The aggregate tokens-per-word ratio is total tokens divided by total whitespace tokens; the mean per-tweet ratio is also reported because the brief says "mean tokens per word".
- **Seeds.** `src/bonus/utils.py::set_seed` sets Python, NumPy, PyTorch, and CUDA seeds from the config seed. Setting `PYTHONHASHSEED` at runtime has no effect on an already-running interpreter; split reproducibility relies on `train_test_split(random_state=seed)`.

## Phase C — AraBERT v02 reproduction training

- **Default seed.** The baseline seed defaults to 42 to match the Phase B split seed. It remains configurable; the paper does not specify a seed for model initialization or minibatch order.
- **Tokenizer and batching.** The tokenizer is loaded from the configured pretrained model. Each example is tokenized with truncation at the configured maximum length, and padding is added dynamically to the longest sequence in each batch.
- **Architecture and loss extension point.** The default model is `AutoModelForSequenceClassification` with its standard classification head and cross-entropy loss. Registries for model and loss factories let later experiments replace pooling, heads, or losses without changing the trainer.
- **Batch order and device.** Training rows are shuffled each epoch with a seeded DataLoader generator; validation rows retain CSV order. The default device is CUDA when available and CPU otherwise, with an explicit device override available to the caller.
- **Run determinism.** Deterministic PyTorch algorithms are requested with warning-only behavior. Data loading uses zero workers and a seeded generator; its state is saved after each epoch and restored on resume. These reproducibility controls are implementation choices beyond the paper. GPU runs are not bit-identical even with deterministic algorithms requested in warning-only mode.
- **Gradient clipping.** No gradient clipping is applied. This is a project decision because the paper does not specify gradient clipping.
- **Unsupported optimizer controls.** Training raises an error if a scheduler is configured or `warmup_steps` is nonzero; these controls are not implemented in this baseline loop.
- **Training and validation metrics.** The full supplied validation split is evaluated at every epoch. Loss is the example-weighted mean batch loss. Precision, recall, and F1 use fixed label IDs and `zero_division=0`; weighted averages use true-class support. The confusion matrix uses row=true and column=predicted in NEG, NEU, POS order. The hand-built metric check follows these definitions.
- **Evaluation RNG isolation.** Evaluation-only passes must not consume the global RNG; this keeps the RNG trajectory of new runs identical to the seed 42 run.
- **History format.** `history.csv` contains one row per completed epoch, with prefixed train and validation aggregate metrics, per-class metrics, losses, and a JSON-encoded confusion matrix. The last checkpoint is the canonical resume state; resume rewrites history from that checkpoint before continuing, so a stale CSV cannot duplicate epochs.
- **Checkpoint selection and writes.** A best checkpoint is written when validation macro F-PN strictly improves; ties keep the earlier checkpoint. Each checkpoint is first written to a temporary file in the same directory and atomically renamed into place. When the best score improves, the best checkpoint and its validation predictions are written before the last checkpoint; the last checkpoint is written after the epoch artifacts and acts as the epoch commit marker. Both checkpoint files retain the same full state: model and optimizer, completed epoch, full history, best score, RNG states, batch-loader generator state, and mixed-precision scaler state. This checkpoint format, write order, atomic write, and tie rule are implementation choices.
- **Run config snapshot.** Each run stores its config, resolved data/output paths, effective run settings, seed, and current Git commit hash in `config.json`. Resume requires the saved snapshot to match. If resuming an older run without a snapshot, training reports that it cannot verify the earlier config and records the current one.
- **Validation predictions.** The run directory's `validation_predictions.csv` stores zero-based CSV row index, true label ID, and predicted label ID for the best validation epoch. A helper can regenerate this file from `checkpoint_best.pt` using validation data only.
- **Smoke workflow.** The notebook defaults to CPU runs on the first 200 train and 200 validation rows. Two same-seed runs each complete one initial epoch, one is resumed to epoch 2, and a separate run completes two epochs uninterrupted; the resumed epoch-2 metrics must match. It also checks identical first-epoch histories, fixed hand-calculated metrics, the `_read_frame` test filename guard, actual test CSV read count, and Git ignore behavior. The validation subset keeps the CPU smoke workflow short; the baseline run uses the complete validation split. These smoke checks are implementation validation, not paper methodology.
- **Held-out evaluation guard.** Test evaluation is a separate explicit function. It creates an exclusive per-run marker before reading the test CSV and refuses every subsequent attempt for that run directory, even if the first attempt failed partway through. This conservative one-attempt rule is an implementation choice to prevent iterative use of held-out labels.
- **Run location.** Checkpoints and smoke artifacts are written under the already ignored `checkpoints/` directory. The training interface accepts train and validation CSV paths only; it has no test path setting.
- **Colab workspace.** The full-run notebook assumes the project folder is in Google Drive at `/content/drive/MyDrive/mizan-arabert-sentiment`; this is a configurable notebook path. Keeping the project and checkpoints in Drive is intended to preserve resume state across Colab runtime interruptions.

## Phase D: three-seed baseline reproduction

- Select each run's best epoch by the highest validation macro F-PN. Exact ties select the earliest epoch, matching the trainer's strict-improvement checkpoint behavior. The last epoch is also reported as a separate secondary view.
- Across-seed standard deviations use the sample standard deviation (`ddof=1`), for both best-epoch and last-epoch summaries.
- Seed 42 reuses the pre-snapshot run produced with Phase C code at commit `b981c05`, before the hardening fix. Its provenance is recorded here manually because no `config.json` existed for that run; the Colab notebook verifies a ten-row history with epochs 1 through 10 and both checkpoint files before any new training. Do not create a `config.json` in the seed 42 directory.
- Seeds 43 and 44 use the current code and receive the trainer's normal `config.json` snapshots. Their output directories are separate so an interrupted run can resume independently.
- GPU execution is not bit-identical across repeated runs. Seeds and deterministic algorithm settings reduce variation, but GPU kernels can still introduce non-determinism.
- The paper's development split counts are 482 / 550 / 223, while this project's frozen validation split counts are 462 / 575 / 218. This difference can affect the reported validation metrics.
- The paper comparison uses the published validation accuracy of 74.98% and weighted F1 of 74.90%. The report gives absolute differences in percentage points. Its rough one-standard-error reference uses the binomial standard error for accuracy at 1,255 validation examples; the same threshold is only a scale reference for weighted F1, which is not binomial.
- Aggregation reads validation histories only. The notebook does not perform held-out evaluation.

## Phase E: enhancement screening

The following are project decisions for this screening protocol; they are not claims about the paper:

- Each candidate is an independent single-change experiment, initially run with seed 42 for ten epochs using the frozen data, preprocessing, split, batch size, learning rate, optimizer, and maximum sequence length.
- Mean pooling uses the last hidden state and attention mask: sum only non-padding token states and divide by the count of unmasked tokens (clamped to at least one). It bypasses the BERT pooler. The head is one linear classifier with dropout probability 0.1.
- Class-weighted cross entropy uses training-split counts only. For class `c`, the weight is `N / (K * n_c)`, where `N` is the training count, `K` is the number of classes, and `n_c` is that class's training count. Weights are not normalized further.
- Focal loss uses gamma 2.0 by default, no class weights, and the mean of per-example `-(1 - p_t)^gamma * log(p_t)` losses.
- Layer-wise learning-rate decay uses factor 0.9. The classifier, pooler, and top encoder layer use the configured baseline learning rate. Encoder layer `i` of `L` layers uses `base_lr * 0.9 ** (L - 1 - i)`; embeddings use `base_lr * 0.9 ** L`.
- The richer head has one 256-unit hidden layer, ReLU activation, dropout probability 0.1 before the hidden layer and after its activation, then a linear three-class output layer.
- Every newly added linear layer is initialized with a zero bias and normal weights using the encoder's `initializer_range`, matching `BertForSequenceClassification` classifier initialization.
- A gain smaller than one Phase D best-view standard deviation is marked inconclusive. If the top two candidates are within one such standard deviation on macro F-PN, screening proposes rerunning those two with seeds 43 and 44 and requires approval before that follow-up.
- A candidate is selected only when the top candidate beats the baseline seed 42 macro F-PN by more than one Phase D best-view standard deviation; otherwise no candidate is selected unless the top-two rule proposes a follow-up for approval.
- The initial comparison uses one seed and cannot estimate candidate-specific seed variance. Phase D standard deviations provide a noise scale, not a guarantee of significance.
- GPU runs may not be bit-identical across repetitions because some kernels remain non-deterministic.
- Only validation histories are read for selection and reporting. The held-out test CSV is never read or referenced.
